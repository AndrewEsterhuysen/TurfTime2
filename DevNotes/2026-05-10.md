# Dev Session Notes — 2026-05-10

## Session Goals
Improve responsiveness of the swipe and drag-to-reorder gestures on the game roster screen (`GamePage`).

## 1. Swipe Responsiveness — Logging off the UI Thread

**Problem:** Swipe left/right to change player positions was sluggish because logging operations (Firebase auth, Firestore writes) were blocking the UI thread.

**Changes:**
- `GameViewModel.cs` — `SetPlayerPosition` and `ReorderPlayer` now fire-and-forget logging via `Task.Run(...)` so the UI updates immediately.
- Firebase warm-up is now triggered during `InitialiseAsync` before cloud load so the first swipe pays no cold-start penalty.

## 2. Drag-to-Reorder — Initial Responsiveness Fix

**Problem:** Drag-to-reorder required holding for a couple of seconds before anything happened.

**Root cause:** Intent threshold (12dp) was too high; there was no visual feedback until the drag indicator appeared on a neighbouring row (~52dp away); swipe/drag arbitration was biased towards swipe for diagonal movements.

**Changes in `GamePage.xaml.cs`:**
- Lowered `IntentThreshold` from `12` → `6` dp.
- Raised `SwipeThreshold` from `80` → `90` dp.
- Added `SwipeDragBias = 1.5` — requires `|dx| > |dy| * 1.5` to commit as swipe; ambiguous/diagonal movements now default to drag.
- Added live `TranslationY` on the dragged row so it follows the finger immediately from the moment intent is committed.
- `_dragStartX` / `_dragStartY` captured at intent-commit time so the row starts translating from zero (no positional jump).
- `row.TranslationY = 0` reset added on `Completed`/`Canceled`.

---

## 3. Drag Row Tracking — Finger Lag Fix

**Problem:** The dragged row lagged behind the finger; the gap grew with drag distance.

**Root cause:** An incorrect density division was applied to `e.TotalX/Y`. MAUI's `PanGestureRecognizer` already delivers coordinates in dp — dividing by device density (e.g. 3× on a Pixel) caused the row to move at 33% of finger speed.

**Fix:** Removed the density conversion entirely. `e.TotalX/Y` are used directly.

---

## 4. Drag Detection — Ghost/Missed Touch Fix

**Problem:** Attempting to drag sometimes had no effect; appeared as if two rows were competing for the same touch.

**Root causes identified:**
1. `GestureStatus.Started` from an adjacent row (when finger was near a row boundary) overwrote `_panRow`/`_panPlayer`, silently abandoning the active drag.
2. `Running` and `Completed` used the event `sender` (which could be a different row) rather than the locked `_panRow`.
3. The 3dp gold `BoxView` gap between rows had no gesture recognizer — touches landing on it were swallowed (dead zone).

**Changes in `GamePage.xaml.cs`:**
- `Started`: Added guard `if (_panRow is not null) break;` — first touch owns the sequence.
- `Running`: Introduced `activeRow`/`activePlayer` locals from `_panRow`/`_panPlayer` — all movement applied to the locked row regardless of which sender raises the event.
- `Completed`/`Canceled`: Same — uses `endRow`/`endPlayer` from locked state.

**Changes in `GamePage.xaml`:**
- Moved `PanGestureRecognizer` from inner `Grid` up to the `StackLayout` root of the item template, so the `BoxView` indicator gap is covered and the entire row area is touch-responsive.
